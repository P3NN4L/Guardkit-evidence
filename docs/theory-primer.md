> 定位：`STUDY-GUIDE` 教你"怎么理解、怎么讲"；`walkthrough` 教你"答辩怎么走"；**本文回答"为什么非这样不可、原理是什么"**。
> 读法：每节四段——是什么 → 为什么 → 我们怎么做的 → 答辩一句话。全部用类比，不预设技术背景。

# 〇、总原理：这个项目的一切决定都源自一张成本表

May 收到换账户消息，只有两个选择，**两个方向都有代价**：

| | 是骗局 | 是真的 |
|---|---|---|
| **转账** | 亏 HK$85,000（灾难） | 顺利付款（正常） |
| **不转** | 保住钱（正常） | 得罪供应商、违约（麻烦） |

**不对称在哪**：漏过一个骗局（亏 8.5 万）比延误一笔付款（麻烦几天）贵得多——但误报太多，工具就没人用。整个项目的每个设计都在这对矛盾里找位置：

> **宁可把可疑的事交给人工，绝不代替人下结论。**（所以"永不自动拦截"）

这句话背后的学科原理叫 **human-in-the-loop**（人在回路）：机器做初筛提效，但高代价决策的最终责任留在人身上。医院急诊的"分诊护士"就是这个模型——triage 这个词本来就是医院词汇，方向 E 的官方示例句直接用了它。

# 一、为什么要"数据库"，Excel 不行吗

**是什么**：关系数据库 = 把业务拆成若干张"各管一事"的表，表与表之间用编号互相引用。

**为什么 Excel 不行**：想象把所有东西塞进一张大表——每行一条判决，顺便塞上消息原文、依据原文、机构名、规则名。会发生三件事：

1. **同一事实重复一万次**：每条判决都抄一遍"香港警务处《警聲》https://police.gov.hk/..."，某天链接变了要改一万行，漏一行就是错数据；
2. **回答不了反向问题**：「这条官方依据，支撑过哪些判决？」——Excel 里没有"依据"这个独立对象，它只是判决行里的一坨文字；
3. **没有约束**：任何人在任何格子里能写任何东西，"已复核"的判决可以没有复核人。

关系模型用三个动作解决：**拆实体**（每个稳定的业务概念一张表：机构、文档、段落、消息、判决、规则）→ **设主键**（每行有唯一身份证）→ **用外键引用**（判决行只存"依据段落编号 17"，不存原文本身）。同一事实只存一处（教科书叫规范化，normalization），改一处全局生效，反向问题变成一条 JOIN 查询。

**我们怎么做的**：8 张表。注意一个容易问的点——**为什么"段落"要单独一张表，不能存在文档表里一整篇？** 因为证据的最小可信单元是"一段话"而不是"一份文档"：判决要引用的是"供應商聲稱更換付款賬戶，必須先聯絡對方確認"这一句，引用粒度越细，越能防止"整篇文档里某处恰好提过"式的含糊依据。

**答辩一句话**：
> "我们按'每个事实只存一处、每个判断可回溯'的原则建了 8 张表；判决和证据是两张表，中间用一张连接表把'哪个判决引用了哪段原文'变成数据库里的硬约束，不是口号。"

# 二、为什么一半用表、一半用 JSON（结构化 vs 非结构化）

**是什么**：课程 §1.5 要求同时管理结构化数据（表）和非结构化/半结构化数据（文本、JSON），并让两者逻辑关联（Integration）。

**为什么**：两类数据**性质不同**——
- 消息、判决、机构：字段固定（分数就是小数、档位就是三选一），天然适合表格，能算能筛；
- 官方文档的原文段落：长短不一、中英混杂、还嵌着链接和日期——硬塞进表格列里既浪费又难保真。

**我们怎么做的**：文档的**原文和元数据**放 JSON 文件（`data/evidence_documents.jsonl`，一行一份、字段灵活），入库时抽取可查询的元数据进表（`evidence_documents`），逐字段落进 `evidence_passages`。这样原文保真（JSON 不动它）+ 查询方便（表能 JOIN）。

还有一个容易忽略的点：**内容指纹（hash）**。对每份文档算一个 SHA-256 指纹存进表——将来页面改了/删了，我们能证明"当时抓的快照内容就是这份"。类比：会计不只要发票复印件，还要骑缝章。

**答辩一句话**：
> "结构化进表、非结构化进 JSON 保留原文，两边用编号关联；每份证据带 URL、抓取日期、内容指纹三件套——这是审计上的'凭证归档'标准。"

# 三、打分引擎：它凭什么给消息打分（够用版原理）

**是什么**：`engine/scorer.py` 是一个**冻结的打分函数**：输入一条消息文本，输出 (预测, 校准分, 原始分)。我们**只调用、不修改**。

**原理四步**（知道到这个深度就够答辩）：

1. **切碎片（n-gram）**：把"換咗收款戶口"切成 1 字、2 字、3 字的碎片（換/收款/款戶/戶口/收款戶…）。为什么按字不按词？中文没有空格，"分词"本身是个难题；按字切不需要词典，粵语口语也能覆盖。
2. **查权重**：模型文件（`models/radar.json`）里存着每个碎片"对判断 scam/normal 的贡献度"（训练时从上万条真实消息里学出来的统计规律）。碎片命中越多、贡献越大。
3. **softmax 概率**：把各类贡献度折算成"是骗局的概率"。
4. **Platt 校准**：模型原始输出容易极端（动不动 0.999），校准把"模型的自信"调整成"历史上同分数消息真实的骗局比例"——让 0.9 真的大约对应九成概率。这就是 `p_cal`（校准分）和 `p_raw`（原始分）两个数的来历。

**它从哪来、为什么不能改**：组员课程前的先期工作（公开仓 + npm 包，提案 §4 已申报）。三个理由冻结它：① 课程考的是**数据管理**不是建模；② 改了它，"pinned 依赖"的申报口径就破了；③ 有一致性测试盯着（`test_parity.py`），改一个字节都会红。

**答辩一句话**：
> "引擎是个黑盒打分器，n-gram 统计模型加概率校准；我们申报它是先期工作、按依赖冻结，课程评估的是我们怎么管它的输入输出。"

# 四、白名单：为什么"三个条件全中"才放行

**是什么**：有些消息看起来像骗局但其实是真的——银行账单通知、政府津贴通告。白名单就是"识别出这类真通知、把分数压下来"的规则。我们有三个族：

| 规则族 | 逻辑 | 例 |
|---|---|---|
| R-NOTICE 反诈提示 | 反诈主题词 **且** 官方建议词 | 「反詐騙」+「切勿/致電熱線」 |
| R-DOMAIN 官方域名 | 官方域名 **且** 无可疑链接记号 | gov.hk / hsbc.com.hk，且没有 .top/.xyz |
| R-INSTITUTIONAL 机构通知 | 机构通知主题 **且** 官方渠道指引 **且** 无可疑链接 | 賬單/稅務 +「App 內查看」+ 无可疑 URL |

**为什么是"且"不是"或"**：这是**精确率和召回率的取舍**（这对概念贯穿全项目，务必吃透）——
- **召回率** = 骗局里被我们抓住的比例（漏报的反面）；
- **精确率** = 我们报警的里面真是骗局的比例（误报的反面）。
白名单的作用是**降误报**，但宽松的白名单（"或"）会把真骗局也放走——骗子最爱冒充银行。所以三重条件全部命中才放行，**宁可少放、不可错放**。

**为什么规则要存进数据库**（`rules` + `rule_patterns` 两张表）：正则写在代码里，别人只能"信"；存成带版本号的表，就能用 SQL 回答"哪条规则在哪个版本介入过哪些判决"——将来调白名单导致误报变化，能定位到具体是哪条、哪版。这就是"规则即数据"。

**审计链**：白名单压档会覆盖分数，那"引擎本来打了几分"去哪了？`score_raw_before_rule` 字段专门留原始分。类比：会计改账不能涂改原数，要留调账凭据。

**答辩一句话**：
> "白名单三重条件是与逻辑，压误报不冒险；规则本身是带版本的数据库记录，原始分永远留档——改了什么、压了多少，SQL 可查。"

# 五、检索：怎么从 34 段官方文字里找到"那一段"

**问题**：判决卡要引官方原文。108 条消息 × 34 段证据，靠人翻是不可能的，要自动检索。

**中文检索的第一个坑**：检索引擎靠"词"匹配，但中文没空格。"換咗收款戶口"切不出词就废了。我们的解法：**按字切两字碎片（bigram）**——"收款戶口"→ 收款/款戶/戶口。两个相邻字组合足以承载词义，也不需要词典。（引擎打分也用同样的思路，这叫混合策略的一致性。）

**BM25 是什么（人话版）**：它是信息检索领域三十年的标准打分公式（FTS5 内置，不是我们发明的），直觉是两条：
1. **这个搜索词在这段里出现得越多，越相关**（但收益递减——出现 10 次不会比 5 次相关一倍）；
2. **这个词越稀缺，越有区分力**："戶口"在防骗文档里到处都是，基本不加分；"供應商聲稱更換"很稀缺，命中就是强信号。（第二条就是 TF-IDF 思想。）

**为什么还要"文档级聚合"**：一份通告被拆成 5 段，单段都短；而银行的假网站通告短、全是"請即登入…轉賬…"的样板话术，跟任何骗局消息都像。只按段落排名，样板通赢、针对性指南反而排不上。修复：先按段落算分，再把**同一份文档的段落得分加总**让"整份通告"参与竞争，最后取冠军文档里最好的段落。这一步让 MSG-001 的依据从排第 4 的假网站通告，回到排第 1 的警务处 BEC 指南。

**为什么不用 embedding（语义向量检索）**：embedding 把文字变成一串数字坐标，"意思近"的坐标就近——听着高级，但三个代价：需要另一个模型（引入新的黑盒）、结果不可解释（说不出"为什么这段相关"）、要装依赖。课程原话是 embeddings "when they add justified value"——**我们的场景是精确术语命中（供應商/收款戶口/熱線），词面匹配已经够，embedding 没带来可论证的增量**。如实写这个结论是加分项，不是偷懒。

**检索不到怎么办**：如实显示"未检索到足够相关的官方段落（不硬凑依据）"。当前 12 条——全是粤语日常闲聊，分数 0.01–0.10。宁缺毋假：编造依据比没有依据严重得多（课程把 "unsupported outputs" 列为反面）。

**答辩一句话**：
> "中文按字切两字碎片建索引，BM25 标准公式排序，再按'整份通告'聚合防止样板话术文档霸榜；不用 embedding 是因为本场景词面匹配够用、且可解释——这是有课程原文背书的正当结论。"

# 六、血缘：为什么老师点名要它

**是什么**：数据血缘（data lineage）= **这份数据从哪来、经过了什么处理、存在哪、变成了哪个输出**的完整路径。注意它不是"谁经手签字"的操作审计——是数据自身的旅程。

**为什么课程点名**（§2.4 交付物 + §1.6 七能力之一）：因为数据产品的可信度不在于"结果好看"，在于**任何结果都能沿路径倒查回源头**。倒查能力有三用：审计（这个判决凭什么）、纠错（数据错了影响哪些判决）、复现（换个环境还能得到一样的结果）。

**我们怎么做的（两层）**：
1. **图**：`docs/design.md` 的架构血缘视图，每一跳标注背书字段——来源（`source_url`/`accessed_at`/`content_hash`）→ 摄取（`pii_scan`）→ 判决（`model_id`/`model_version`）→ 依据（`retrieval_method`/`rank`）；
2. **硬证据**：组员从 GitHub 拉 tarball 在隔离目录重建，**重建库与提交库逻辑内容逐行一致（8 表全量、含 142 条证据连接），文件大小一致（204,800 bytes；字节差异仅判决时间戳与 SQLite 页头计数器）**——血缘不只是"画了图"，是真的一条命令能复现。

**答辩一句话**：
> "血缘每跳都有字段背书、SQL 可查；而且我们的库是确定性的——同样输入必然重建出同一个文件，这是可复现性的最硬形态。"

# 七、评估：怎么证明它好、更重要的是诚实地说它哪里不好

**是什么**：拿 108 条**已知答案**的消息（label=scam 或 normal，来自真实盲测卷）让系统判，对照"期望 vs 实际"。四个格子（混淆矩阵）：

| | 系统说可疑 | 系统说放行 |
|---|---|---|
| 真骗局 | 抓对（40 条） | **漏报 FN（3 条）** |
| 真正常 | **误报 FP（12 条）** | 放对（53 条） |

由此两个数：**召回率 = 40/43 ≈ 93%**（骗局被抓住的比例）；正常消息放行率 = 53/65 ≈ 82%。漏报的 3 条我们逐条分析过原因（短文本伪付款确认、英文长邮件），误报的 12 条也在 `evaluation/fp-attribution.md` 有历史归因——**说得出"为什么错"比"错得少"更能体现评估质量**，这是课程明说的加分行为（"strong evaluation of difficult cases"、"recognition of limitations"）。

**为什么还要已知困难案例**：只测"会做的题"是自欺。我们主动放进引擎已知会错的题（对话体假借钱、广告类、2025 新骗术）——评估的价值在于画出能力的**边界**，边界诚实的工具才敢用。

**已知局限（主动申报的）**：引擎是 n-gram 模型，老骗术近乎满分，2025 新话术召回缺口（基线 84.2%）；证据页面天然滞后于实时骗术。这些写进评估是**加分的诚实**，藏起来才是风险。

**答辩一句话**：
> "我们有标注池、混淆矩阵、漏报误报逐条归因、困难案例集——评估的目的不是证明完美，是画清楚能力边界。"

# 八、治理：为什么"永不自动拦截"写在第一页

**是什么**：治理（governance）= 数据和决策的**责任结构**：谁能看什么、机器能做什么决定、人怎么复核、出错怎么追责。

**我们的四个治理设计，每个都对应一种真实风险**：

| 设计 | 防的错 | 落地在哪 |
|---|---|---|
| 永不自动拦截 | 机器误判直接造成损失 | 高危只升级（`verdicts` → 人工复核字段 `reviewed_by/at`） |
| 白名单留原始分 | 规则悄悄改写结论、无法追责 | `score_raw_before_rule` 字段 |
| PII 分级处理 | 把别人隐私存进库里 | 个人邮箱/证件号自动脱敏计数；公司热线是通告内容、按口径保留 |
| 数据全标注来源 | 用了不合规/合成的数据还不自知 | `source`/`synthetic_derived`/`generation` 字段，LLM 生成的行永远隔离标注 |

**为什么这是高分项**：课程治理评分描述专门写了 "Do not add generic ethics statements unrelated to the actual project"——**反对泛泛的道德声明，要具体的机制**。别人写"我们重视隐私"，我们写"个人邮箱命中即脱敏、命中数存在哪个字段、公司热线为什么保留"——这是能被 SQL 检查的治理。

**答辩一句话**：
> "我们的治理不是声明，是字段和流程：隐私有扫描管线、误判有人工兜底、规则改动有审计链——每一条都能当场演示。"

# 九、把所有原理串成一段话（终极检验）

> 一条可疑消息进来，一个**冻结的统计引擎**把它切成字碎片、按训练出的权重打出校准概率（三）；三重白名单规则——**存在数据库里、带版本、留原始分**——决定是否压档放行（四）；需要依据时，**bigram 索引加 BM25 公式加文档聚合**从官方通告里找出那一段原文（五）；判决和依据的引用关系由**外键**写死在 schema 里，整条**血缘**每跳有字段背书、整个库可确定性复现（一、二、六）；108 条已知答案的消息画出了系统的能力边界，包括它哪里会错（七）；而所有自动化之上，**永远有人工复核**（〇、八）。
>
> ——这就是把"一个人凭记忆做的判断"，变成"一个组织可复查的记录"的全部含义。
